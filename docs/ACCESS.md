# 배포와 공동작업 권한

2026-10-26 후속 결정. 소스는 공개하고 실행파일의 접근 범위를 구분한다.

| 대상 | 위치 | 접근 |
|---|---|---|
| 소스·개발 방침·진척 | 공개 `issackr580/doctor-glean-pc` | 누구나 열람·fork 가능 |
| 배포용 실행파일·패치 | 같은 저장소의 공개 prerelease | 일반 사용자 다운로드 |
| 개발자용 실행파일·패치 | 같은 저장소의 **협업자 전용 Draft** | 관리자와 쓰기 권한 collaborator만 열람·다운로드 |
| 사용자 계정·세션·개인 진단 | 각 PC 로컬 | Git·릴리스에 포함하지 않음 |

GitHub Draft를 열려면 해당 저장소에 쓰기 권한이 필요하다. 쓰기 권한은 코드·릴리스 편집에도 적용된다. 따라서 관리자가 신뢰하는 소수만 초대하고 Admin 권한을 추가하지 않는다. 누구나 소스를 보거나 PR을 보낼 수 있어도 원본을 직접 수정할 권한이 생기지는 않는다. 소스 공개 상태에서 개발자 기능의 코드도 공개된다.

## 초대와 작업

1. 관리자가 초대할 GitHub 아이디를 명확히 지정한다. 이름·이메일로 임의 계정을 추정하지 않는다.
2. 선정 전에는 쓰기 권한을 주지 않고 fork → PR로 작업할 수 있다. 지정된 collaborator는 이슈별 작업 브랜치 → PR로 진행한다.
3. 초대 수락 후 해당 GitHub 계정으로 로그인해 [Releases](https://github.com/issackr580/doctor-glean-pc/releases)에서 **협업자 전용 Draft**를 연다. 계정·권한이 없으면 404가 정상이다.
4. 개발자용 Draft는 계속 Draft로 유지한다. **Publish release를 누르면 실행파일이 일반 공개된다.** 개발자 실행파일을 공개 distribution 릴리스에 첨부하지 않는다.
5. 본인이 최종 리뷰·병합·배포를 담당하는 운영 규칙을 따른다. GitHub 쓰기 권한 자체는 collaborator의 병합·릴리스 편집도 허용하므로 이 규칙과 실제 권한 범위를 혼동하지 않는다.
6. 협업 종료·권한 변경 때 저장소 접근을 회수한다. 이미 내려받은 파일까지 회수되지는 않는다.

## main과 검증 환경

`main` 직접 push 대신 PR로 변경하고 force push·브랜치 삭제를 금지하는 보호 규칙을 설정한다. 교차 리뷰할 사람이 갖춰지면 승인 1회와 마지막 변경 뒤 재승인을 요구한다. GitHub에서 설정을 읽거나 바꾸려면 repository administration 권한이 필요하다. 현재 연결로 보호 규칙 조회가 403이었으므로, 이 문서만으로 보호가 활성화됐다고 주장하지 않는다. 관리자는 Settings → Branches 또는 Rules에서 실제 규칙을 확인한다.

외부 PR 코드는 먼저 검토하고 실제 계정·토큰이 없는 분리된 검사 환경에서 실행한다. 자동 워크플로·자동 릴리스는 연결하지 않는다. 개발자 진단도 [DIAGNOSTICS](DIAGNOSTICS.md)의 고정 항목만 수동으로 공유한다.

이 방식은 추가 서버나 유료 서비스 없이 GitHub의 저장소·Draft 권한을 사용한다. 과거 본인 전용 초안과 공개 배포 자산을 삭제하거나 덮어쓰지 않는다.
