# 0.1.0-preview.11 — 디톡스 자동 조회의 로그인 진입 복구

2026-10-27. 작업 중이며 아직 게시하지 않았다.

## 문제와 변경

사용자 Windows v10 보고의 10:47 한국 시각 디톡스 조회는 `network_error`, `failure:load_failed`, coverage=false였고 이전 강의1개가 stale로 남았다. 저장 계정과 자동 복구 동의는 있었지만 이번 작업의 디톡스 계정 복구 결과는 없었다. 과거 authenticated 기록을 이번 성공으로 해석하지 않는다. 이 보고만으로 브라우저의 세부 네트워크 원인을 단정하지 않는다.

고정 목록의 로드가 실패하면 CatalogPage.open이 로그인 필요 판독 전에 종료됐고 디톡스에는 자동 조회용 대체 진입이 없었다. 고정 목록의 일반 load_failed에 한해 원래 `https://www.dtalks.kr/login.do` GET을 한 번 읽도록 한다. 이후 기존 CatalogRunner가 로그인 필요를 확인하고 동의한 저장 계정을 한 번 복구한 뒤 새 조회 창을 연다. 단순한 연결 실패를 인증 성공으로 바꾸지 않는다.

인증서·DNS·오프라인·시간초과·취소, 변형된 목록 URL에는 대체 진입하지 않는다. 고정 로그인도 실패하면 중단하고, 자동 복구 동의 해제·보안 확인·기존 불확실 시도 잠금은 유지한다. 복구 뒤 목록이 다시 실패해도 두 번째 로그인 제출은 없다. 기존 stale 목록을 완료된 새 조회로 바꾸지 않는다.

## 검증

Node24.19.0/npm11.9.0에서 `npm test`와 구문 검사를 실행하고, 파일 단위 집계와 별도로 `node --test --test-isolation=none test/*.test.js`의 실제144항목 통과를 확인했다. 기존 코드는 디톡스 대체 진입 관련2항목이 실패했다.

Linux Electron45.0.0/Xvfb 합성 HTTPS는 개발자 관리 창60·자동 작업28·계정90항목을 통과했다. 목록 실패→고정 로그인→동의한 계정1회 POST→인증 확인→원래 목록 판독을 검사했다. 합성 목록의 모호한 메뉴는 review로 중단하여 읽지 않은 목록을 성공으로 만들지 않는다. 동의 해제·보안 확인·로그인 GET 실패는 POST0회, 복구 후 지속 실패는 POST1회이며 두 번째 복구는 없었다. 제출 전 시도 기록·진단의 계정값 제외·모든 검사 창 해제도 확인했다.

컨테이너 OS sandbox 제한으로 검사에만 `--container-no-sandbox`를 사용했다. 제품의 원격 sandbox·contextIsolation·webSecurity·TLS 검증은 유지한다. 최종 묶음·패치·소스 검증과 게시 상태는 준비 후 기록한다. 실제 Windows DPAPI·사용자 계정의 이번 복구와 강의 목록은 재확인 대상이다.

모바일 소스·APK·서명·릴리스·vendor와 에디션별 사용자 데이터·시도 기록·Electron45.0.0·의존성은 변경하지 않는다.
